# Purpose

This document defines the official database naming conventions for the LOUTAS Care Platform.

The objective is to ensure a consistent, readable, scalable, and maintainable database structure across all modules and environments.

These standards apply to PostgreSQL, Prisma schema definitions, migrations, indexes, constraints, and database objects.

---

# Objectives

- Standardize database object names.
- Improve database readability.
- Simplify maintenance.
- Reduce ambiguity.
- Improve collaboration between developers and DBAs.

---

# General Principles

Database objects shall:

- Use meaningful names.
- Avoid abbreviations unless universally accepted.
- Remain consistent across all modules.
- Reflect business terminology.

---

# Prisma Model Naming

Prisma models shall use:

- PascalCase
- Singular nouns

Examples:

```text
Patient
Appointment
Invoice
Payment
Branch
User
```

Avoid:

```text
Patients
tbl_patient
patient_master
```

---

# Database Table Naming

Database tables generated by Prisma shall follow the approved model names.

Use singular business entity names.

---

# Column Naming

Columns shall use camelCase.

Examples:

```text
id
fullName
mobileNumber
dateOfBirth
createdAt
updatedAt
```

Avoid:

```text
Full_Name
patient_name
PatientName
```

---

# Primary Keys

Every table shall contain:

```text
id
```

Primary keys shall use UUID whenever possible.

---

# Foreign Keys

Foreign key columns shall end with:

```text
Id
```

Examples:

```text
patientId
doctorId
invoiceId
appointmentId
branchId
```

---

# Timestamp Columns

Standard timestamp fields:

```text
createdAt
updatedAt
deletedAt
```

Soft delete shall use:

```text
deletedAt
```

instead of boolean flags.

---

# Boolean Columns

Boolean fields should begin with:

```text
is
has
can
```

Examples:

```text
isActive
isDeleted
hasInsurance
canEdit
```

---

# Enum Naming

Enums shall use PascalCase.

Examples:

```text
AppointmentStatus
InvoiceStatus
PaymentMethod
Gender
```

---

# Junction Tables

Many-to-many relationships shall use descriptive names.

Examples:

```text
UserRole
PatientAllergy
DoctorSpecialty
```

---

# Index Naming

Indexes should follow:

```text
idx_table_column
```

Examples:

```text
idx_patient_mobileNumber
idx_invoice_invoiceNumber
```

---

# Unique Constraints

Use:

```text
uq_table_column
```

Examples:

```text
uq_patient_nationalId
uq_user_username
```

---

# Foreign Key Constraints

Use:

```text
fk_child_parent
```

Examples:

```text
fk_appointment_patient
fk_invoice_visit
```

---

# Migration Naming

Migration names shall clearly describe the change.

Examples:

```text
add_patient_allergy_table
create_billing_configuration
add_invoice_discount
```

Avoid generic names such as:

```text
update
fix
changes
```

---

# Audit Tables

Audit-related tables should use:

```text
AuditLog
```

Audit fields should remain consistent across all modules.

---

# Soft Delete

Soft deletion shall use:

```text
deletedAt
```

Records should not be physically removed unless approved.
